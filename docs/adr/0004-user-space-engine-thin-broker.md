# ADR-0004: 会话逻辑在用户态，特权进程只做能力代理

- 状态：已接受
- 日期：2026-10-13

## 背景

RustDesk 把繁重的连接状态机放进提权的服务进程（受控端），`connection.rs` 8000 行、`ipc.rs` 2400 行。以 root/SYSTEM 运行的代码越多，安全审计面越大，系统签名/公证审查越难。

## 决策

- 会话逻辑（状态机、编解码协商、QoS、权限）全部在用户态进程，每会话一个 tokio task（actor）+ 显式状态枚举与转移函数。
- 提权进程（`rd-broker`）是哑的、按平台最小化的能力代理：不解析会话消息、不联网、只接受本机特定 UID/管道 ACL 的连接；IPC schema 版本化（interprocess crate）。capture / input / audio 是候选能力接口，不代表每个平台都必须经 broker，也不代表提权可绕过桌面会话、用户授权或系统安全桌面限制。
- P0 需形成逐平台能力矩阵。Windows、macOS、X11、Wayland 的采集/注入 API 与授权模型分别评估；只有确需提升权限的操作进入 broker，其余留在用户会话进程。v1 不支持的 UAC/锁屏交互必须明确写入产品限制与验收项。

## 后果

- 特权代码量极小、可整体审计；会话逻辑 headless 可测。
- 代价：经 broker 的捕获帧与输入事件可能多一次进程间拷贝；只对实际采用 broker 的路径在 P1/P4 测量 p95 延迟与带宽，不以局域网总延迟预算推定拷贝开销可接受。
