# P2 接收边界修复（2026-10-15）

接收端原先将 Reassembler 的 Stale 与畸形包一样上报为 TransportError。无序视频中，已完成、已过期或落后窗口的分片可能迟到；这些分片不应让健康链路断开。现在 recv 跳过 Stale，继续等候有效帧；Invalid 和 Capacity 仍返回错误，未放宽畸形输入与容量边界。

recv 返回错误时立即替换重组器，释放未完成帧。原实现虽然对象 Drop 时会释放，但调用者保留已关闭句柄时，分片数据仍会留存至 TTL 清理或对象销毁。此修复只保证错误返回后的重组缓存释放；没有声称 worker 关闭瞬间释放、取消 recv 后立即释放，或操作系统 RSS 随之下降。

新增两项确定性回归：在 worker→接收器队列边界注入已完成帧的迟到重复分片和后续有效帧，必须跳过重复并交付后续帧；另预置部分帧、实际停止接收 worker，保留 transport 句柄调用 recv，必须返回 Closed、缓存归零且再次读取仍 Closed。队列边界注入避免无序网络先交付后续帧而掩盖重复分片处理。

首次回归还暴露旧双端测试在视频通道打开前发送零重传视频导致首帧偶发丢失，现改为等待双方真实 ChannelOpen(video) 后发送，不以固定睡眠掩盖握手时序。

验证：启用 rd-app/webrtc 的 app、engine、protocol、transport 定向库回归共 65 项通过（28+11+13+13）；transport/app all-targets 严格 clippy、全工作区格式和 diff 检查通过。此次不是拥塞压力、实际网络丢包或 RSS 验收；这些 P2 缺项继续保留，P1 仍暂缓。
