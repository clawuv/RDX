# P2 开发回环有界重连（2026-10-15）

适用于 `RDX_LOOP_WEBRTC=1` 的同进程双端回环，尚不是局域网或生产认证会话重连。

首次连接失败或运行中断线后，仅对类型化 TransportError 和 Tokio 超时重试。最多追加 3 次连接，依次等待 250/500/1000ms；这是整个运行期的总预算，成功输出视频不会重置。能力不兼容、配置、捕获、协议解析或编解码错误立即停止。关闭 UI 会取消正在建立的连接、媒体任务或退避等待。

每次失败的异步调用结束并释放旧对象后，先清空 UI 旧画面，再新建 UDP/ICE/DTLS/SCTP、能力交换与心跳、媒体编号及编解码器。Windows 首次将显示器索引解析为名称，后续重新枚举按该名称精确匹配；目标缺失或名称歧义报错，不切换到其他屏幕。采集本身的失效恢复继续沿用原有独立退避逻辑。

验证覆盖：总计初次加 3 次尝试、能力不兼容不重试、关闭 UI 立即取消长退避，以及旧画面→清空→新连接解码画面的切换。切换测试两代都经过真实本机 WebRTC，首代输出 128×96 后实际销毁发送端 transport、停止 worker；接收端须在 10 秒内自行返回类型化 TransportError，重连监督器据此新建连接输出 160×120。测试不再直接注入模拟 Closed 错误。单项实测总耗时 9.88 秒（包含两次连接建立、编解码、断线等待和重连，不是纯重连耗时）。这属于真实本机对端停止故障，仍非 UDP 丢包、拔网线或双机网络切换测试。另修正旧媒体序号回绕测试：先完成能力交换，避免在握手前发送零重传视频导致偶发首帧丢失。

验收：`cargo test -p rd-app --features webrtc --lib --locked` 28 项通过；`cargo clippy -p rd-app --features webrtc --all-targets --locked -- -D warnings` 与不启用 webrtc 的 `cargo check -p rd-app --bin rd-loop --locked` 通过。格式与 diff 检查通过。

尚未验证实际断网后恢复、双机信令和网络切换。没有把 SessionState 从 Closed 强行改回 Connect，也未伪造认证事件；生产重连须创建新会话 actor 并完成真实认证及 Active 门控。P1 剩余验收继续延期，P2 不视为整体验收通过。
