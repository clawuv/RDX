# P2 首周 spike：str0m 与 tokio 桥接（2026-10-15）

## 结论

**桥接模式可行**（PLAN.md P2 标注的最大不确定点，消除）。str0m 0.24.1 以纯 Rust crypto（`rust-crypto` feature）接入 rd-transport（feature `webrtc`，默认关闭，wasm 侧不拉入原生依赖）：同步 `Rtc` 与其 UDP socket 全部归一个专用线程，tokio 侧只通过 channel 交互（命令进、事件出），线程内按官方 chat 示例的 poll_output/Transmit/Timeout 模式驱动。本机双实例经**真实 ICE + DTLS + SCTP** 在 127.0.0.1 UDP 上建立 DataChannel 并双向交换帧。初始 spike 的 4 项测试和后续分片/恢复回归均通过。

## 实现要点（crates/rd-transport/src/str0m_impl.rs）

- `Str0mTransport`：实现 `Transport` trait（send/recv Frame）；事件通道暴露 `ChannelOpen`/`IceConnected` 生命周期事件，以及本地缺片通知和对端关键帧请求，供上层观测。
- SDP 交换属信令（P3）：`new_offerer`/`new_answerer`/`accept_answer` 显式传递 offer/answer；`connect_pair` 以进程内交换完成握手，供 P2 局域网联调与测试。
- 发送路径：命令只入队，线程在通道打开后按 SCTP 可用窗口（`Channel::write` 返回 false 即背压）冲刷；tokio 侧从不阻塞。
- 接收路径：控制和视频使用独立有界队列；`recv_control` 保留普通控制消息，`recv` 负责分片重组、过期检测和关键帧恢复请求；生命周期与恢复事件由 `next_event` 观测。
- 线程退出：停止标志或命令通道断开（try_recv Disconnected）即结束，`Drop` join 至多一个轮询周期（≤100ms）。
- 期间踩坑记录：tokio 运行时线程上不可 `blocking_send`（用 try_send + 断开兜底）；`Input::Receive(Instant, Receive)` 而非旧文档的 `Input::Packet`；锁文件重解析遇 zeroize_derive 索引缓存陈旧，`cargo info` 刷新后自愈。

## 验证

- `cargo test -p rd-transport --features webrtc`：9 项通过（双向帧交换、分片重组、控制/视频隔离、关键帧恢复和线程干净退出）。
- `cargo clippy -p rd-transport --features webrtc --all-targets -- -D warnings` 通过；默认 feature（不拉 str0m）构建与测试不受影响。
- wasm 核心边界复验：`rd-protocol` / `rd-engine` / `rd-crypto` 在更新后的锁文件下仍编译 `wasm32-unknown-unknown`（本机此前未装该 target，已补装验证）。
